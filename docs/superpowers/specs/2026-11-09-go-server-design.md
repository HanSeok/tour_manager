# Go 서버 전환 설계 (초안)

상태: 초안. 사용자 결정과 작성자 판단을 구분해 표시한다. 구현 전 검토 필요.

## 1. 목적
- 서버를 Apps Script에서 Go(Docker)로 옮기고, 여행 후 날짜별 타임라인(결제·장소·사진)과 여행 단계별 화면(계획/진행/완료)을 제공한다.
- 사진은 Google Photos와 연동한다.

## 2. 결정 사항
**사용자 결정**
- 서버는 Go, Docker 구동. 화면(prototype/ JS)은 유지.
- Google 계정 2개(소유자 + 동행자)를 연동한다.
- 데이터는 최대한 Google에 저장하고, SQLite는 연동 정보 위주로만 쓴다.
- UI는 Google 데이터와 SQLite를 조합해 보여주고 입력받는다.

**작성자 판단 (검토 필요)**
- Google이 원본, SQLite는 지워도 재로그인·재동기화로 복구되는 저장소로 둔다.
- 여행 단계는 오늘 날짜와 설정 탭의 시작·종료일로 자동 판정한다.
- 한 스프레드시트 = 한 여행. 다중 여행 목록은 범위 밖.
- 소유자 계정 토큰은 서버가 보관(현 executeAs와 동일), 동행자는 로그인(신원)과 본인 사진 선택에만 OAuth를 쓴다.

## 3. 저장소 매핑
| 데이터 | 원본 | SQLite |
|---|---|---|
| 설정, 허용 이메일 | 시트 `설정` | 읽기 캐시 |
| 지출 | 시트 지출 탭 (기존 10컬럼) | 읽기 캐시 |
| 동선 | 시트 `_동선`, `_출발` | 읽기 캐시 |
| 방문 기록 | 시트 `방문기록` | 읽기 캐시 |
| 사진 | Drive 폴더(원본) + 시트 `사진`(메타) | Photos↔Drive ID 매핑 |
| 일정 | 캘린더 | syncToken, 읽기 캐시 |
| 장소 | My Maps(읽기 전용) | KML 캐시 |
| 이동시간, 영업시간 | 없음(재조회 가능) | 캐시 |
| 토큰, 세션 | 없음 | 암호화 저장 |

## 4. UI 조합 규칙
1. 화면은 저장소를 모른다. 서버가 도메인 API(`boot`, `refresh`, 쓰기 함수들)로 합쳐서 내려준다.
2. 읽기: SQLite 스냅샷을 먼저 반환하고(빠름), 백그라운드에서 Google 변경 여부를 확인해 갱신한다. 변경 감지는 Calendar syncToken, Drive `modifiedTime`(시트·폴더)처럼 값싼 호출을 먼저 쓴다.
3. 쓰기: 서버가 검증 → Google에 기록(시트는 RAW 입력) → 스냅샷 갱신 → 병합된 값을 반환한다. Google 쓰기가 실패하면 실패를 그대로 돌려주고, 클라이언트의 기존 outbox가 같은 클라이언트 ID로 재시도한다(중복 방지).
4. 화면 표시: 스냅샷 기준 시각을 노출하고("N분 전 기준"), 저장 대기 항목은 "⏳ 전송 대기"로 표시한다(기존 동작 유지).
5. 타임라인은 여러 저장소의 결과를 한 줄로 합친다: 결제(시트) + 방문(시트) + 사진(Drive/시트) + 일정(캘린더) + 동선(시트). 합치는 로직은 이미 `prototype/timeline.js`에 있다.

## 5. API 계약 (기존 서버 함수 → HTTP)
기존: `bootstrap`, `refresh`, `diagnose`, `addExpense`, `updateExpense`, `deleteExpense`, `saveState`, `registerRoute`, `unregisterRoute`, `getTravelTimes`. 메뉴 기능(`showEditLinks`, `rotateEditKey`, `createTripCalendar`)은 관리 화면으로 옮긴다.
신규(안): `addVisit`, `deleteVisit`, 사진 선택 세션 시작/완료, `listPhotos`.
전송은 `POST /api/<함수명>` JSON. 함수 이름과 인자 순서는 유지해 `remote.js` 변경을 최소화한다.

## 6. 비목표
- My Maps에 장소 쓰기(API 없음), 다중 여행 관리, 공개 사용자용 무설치 배포(legacy 브랜치에 보존).

## 7. 제약·위험
- Sheets 읽기 쿼터 → 서버 캐시와 배치 읽기 필수.
- 시트는 행 단위 잠금이 없다 → 추가는 안전, 덮어쓰기는 날짜 단위로 쓰고 마지막 쓰기 승.
- Photos 이미지 주소는 만료 → Drive로 복사 저장.
- Routes API 과금, 테스트 모드 OAuth 토큰 만료 가능.

## 8. 미확인 (공식 문서로 재확인)
- Photos Picker 스코프의 검증 요건, Drive 최소 스코프로 충분한지, OAuth 테스트 모드 토큰 정책, Routes API 무료 한도.

## 9. 단계
1) API 계약서·시트 탭 스키마 확정 2) Go 골격(정적 서빙, 로그인, 설정) 3) 지출·동선 포팅 + go test 4) 캘린더·지도·이동시간 5) Docker 이미지·운영 서버 배치 6) 방문 기록 → 사진

## 10. 권한과 작성자 표시 (추가)

**사용자 결정**
- 동행자에게 권한을 주면, 그 동행자는 서버에서 해당 여행을 수정할 수 있다(Google 리소스를 직접 공유하는 방식이 아님).
- 누가 추가한 일정(항목)인지 표시한다.

**작성자 판단 (검토 필요)**
- 권한 목록은 시트 `멤버` 탭(이메일, 표시 이름, 역할)에 둔다. 역할: 소유자 / 편집자 / 보기. SQLite에는 캐시만 둔다. 소유자가 탭을 고치거나 관리 화면에서 추가·삭제한다.
- 로그인한 Google 이메일이 `멤버`에 있어야 접근할 수 있다. 서버는 소유자 토큰으로 시트·캘린더·Drive에 쓰므로 동행자에게 Google 공유 권한이 필요 없다. 편집 키 링크는 폐지한다.
- 권한 회수는 `멤버` 행 삭제로 하며, 멤버 캐시 유효시간(1분 이하)과 세션 재검증으로 지연을 제한한다.
- 서버 권한 검사가 기준이고, 화면은 `boot` 응답의 `me {email, name, role}`로 편집 컨트롤을 숨기기만 한다.
- 소유자 토큰으로 대신 쓰기 때문에 Google 쪽 기록자는 모두 소유자로 남는다 → 작성자는 별도 컬럼으로 기록한다.

**작성자 기록**
| 대상 | 기록 방법 |
|---|---|
| 지출 | 컬럼 추가: 기록자(이메일), 수정자 (결제자와 별개) |
| 방문, 사진, 동선(날짜 행) | 기록자, 수정자 컬럼 |
| 서버가 만든 캘린더 일정 | 이벤트 extendedProperties(비공개)에 기록자 + 설명에 표시 이름 |
| 구글 캘린더에서 직접 만든 일정 | 작성자 미상 → "캘린더 직접 입력"으로 표시 |
| 전체 | 시트 `변경이력`(append-only: 시각, 이메일, 대상, ID, 동작) — 복구·분쟁 확인용 |

**화면**: 타임라인·지출·일정의 각 항목에 작성자 이름 칩을 표시하고, 사람별 필터를 둔다. 표시 이름은 `멤버` 탭에서 가져온다.

**사용자 결정**: 편집자는 다른 사람이 만든 항목도 수정·삭제할 수 있다. 대신 모든 변경을 `변경이력`에 남기고(삭제는 삭제 전 값 포함) 복구할 수 있게 한다. 동시 수정 충돌은 항목의 수정시각 비교로 감지한다(상세는 api-schema 문서).

## 11. 데이터 소유 (추가)

**사용자 결정**: 서버에 저장되는 데이터는 모두 해당 여행의 관리자(소유자) 데이터로 저장한다.

**귀결**
- 시트, 캘린더, Drive 폴더, `멤버`·`변경이력` 탭은 전부 소유자 계정 안에 있다. 동행자가 입력해도 Google 쪽 소유자는 소유자다(작성자는 §10 컬럼으로 구분).
- 동행자 사진은 Photos에서 고른 뒤 소유자 Drive 폴더로 복사한다 → 소유자 Drive 용량을 쓴다. 동행자의 Photos 원본은 동행자 라이브러리에 그대로 남는다.
- SQLite 파일과 볼륨은 서버 운영자(소유자)가 관리한다.

**작성자 판단 (검토 필요)**
- 동행자의 Google 토큰은 저장하지 않는다. 로그인(신원 확인)과 사진 선택 시점에만 일시적으로 쓰고 버린다. 저장하는 refresh token은 소유자 것 하나뿐이다.
- 소유자 토큰이 만료·회수되면 모든 쓰기가 멈춘다(단일 장애점). 진단 화면에서 상태를 보여주고 재로그인 경로를 둔다.
- 동행자에게 "입력한 내용은 소유자 Google 계정에 저장되고 소유자가 볼 수 있다"고 로그인 화면에 알린다.
- 여행 종료 후 동행자에게 사본을 주는 기능은 범위 밖(필요 시 추후).

## 12. 후보 방식 일정 (슬롯) (추가)

**사용자 결정(개념)**
- 계획 단계에서는 방문할 수도 있는 곳을 여러 곳 추가해 둔다. 실제 여행에서는 그중 몇 곳만 방문한다.
- 쉬는 곳(카페 등)도 일정에 들어갈 수 있다.
- 점심처럼 시간대마다 가면 좋은 곳 3~4곳을 후보로 두고, 현지에서 그 시간에 의견을 모아 한 곳을 방문한다.
- 방문했는데 문이 닫혀 있으면 후보 목록에서 다른 곳으로 바꾼다.

**작성자 판단 (검토 필요)**
- **슬롯 모델로 통일**: 일정의 한 칸(슬롯) = 라벨(점심·카페·자유 …) + 후보 장소 N개 + (확정된 장소) + 체류 시간. 지금의 "장소 하나"는 후보가 1개인 슬롯으로 본다(자동 확정). 기존 데이터는 읽을 때 후보 1개 슬롯으로 변환한다(호환).
- **후보가 0개인 슬롯**("쉬는 시간", "미정")도 허용한다. 위치가 없으므로 이동시간 0, 체류 시간만 차지한다.
- **계획 단계 계산**: 확정 전에는 "임시 선택"으로 도착·출발 시각을 계산한다. 순위: 도착 시 영업 중(대기 30분 이하) > 영업시간 미상 > 체류 시간 부족 또는 30분 넘는 대기(브레이크타임 등) > 휴무·마감, 같으면 목록 순서. 확정된 후보가 있으면 항상 그것을 쓴다. 화면에는 후보마다 그 시각의 영업 가능 여부(휴무·브레이크타임·마감)를 표시한다.
- **진행 단계**: 슬롯의 후보와 현재 영업 상태를 보여주고, 한 곳을 확정한다. 방문하면 방문 기록(결과=방문)이 생긴다. 닫혀 있으면 "닫힘"(사유 포함)으로 기록하고, 그 후보를 제외한 채 남은 후보에서 다시 고르거나 장소 목록에서 새 후보를 추가한다. 슬롯 전체를 건너뛸 수도 있다.
- **후보 결과는 방문 기록에서 파생**한다(슬롯·장소별 최신 기록). 별도 상태 열을 두지 않아 원본이 하나로 유지된다.
- **타임라인**: 방문한 곳을 보여주고, "닫혀서 건너뜀" 기록은 흐리게 한 줄로 보여준다. 선택되지 않은 후보는 접어서 보여준다.
- **의견 모으기**: 앱 안 투표는 하지 않는다. 의견은 현지에서 말로 모으고, 편집자 누구나 한 곳을 확정해 기록한다(누가 확정했는지는 수정자로 남는다).

**사용자 결정**: 의견 모으기는 앱 안 투표 없이 "확정만 기록"한다. 투표는 필요해지면 나중에 추가한다(슬롯·후보 구조는 그대로 확장 가능).
